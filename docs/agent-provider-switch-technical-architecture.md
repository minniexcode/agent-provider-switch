# agent-provider-switch Technical Architecture

Current version: `1.2.0`

Current fact sources:

- [`PRD/agent-provider-switch-prd-v1.2.0.md`](./PRD/agent-provider-switch-prd-v1.2.0.md)
- [`Design/agent-provider-switch-v1.2.0-design.md`](./Design/agent-provider-switch-v1.2.0-design.md)
- [`PRD/agent-provider-switch-prd-v1.1.0.md`](./PRD/agent-provider-switch-prd-v1.1.0.md) for Claude defaults and compaction
- [`cli-usage.md`](./cli-usage.md)

`1.2.0` implements the shared provider workflows and the target adapters described below: the six
provider verbs are written once, and a target contributes an adapter rather than a parallel set of
services. Stored formats, native configuration rules, the JSON envelope, and the error vocabulary
are unchanged from `1.1.3`.

## Layers

```text
src/cli.ts          process entrypoint
src/commands/       argument parsing, command registry, help, dispatch, target bindings and presenters
src/cli/output.ts   pure human and JSON rendering; src/cli/report-lines.ts holds the shared text helpers
src/interaction/    the shared provider chooser, over an injectable prompt runtime
src/app/            shared workflows and command use cases
src/app/targets/    the target adapters, the shared report composer's ports
src/domain/         provider/config/backup/target types and pure rules
src/storage/        filesystem repositories and TOML/auth helpers
src/runtime/        Codex CLI probing and invocation helpers
```

The six provider verbs live in `src/app/provider-workflows.ts` and end at one
`commitProviderChange()` boundary, which is the only caller of `runMutation()` for a provider
write. Each target supplies a `ProviderAdapter` under `src/app/targets/` — its records, native
plans, matching and payload views, and report reads. An adapter may not import the workflow module,
`run-mutation.ts`, the registry repo, the shared chooser, or the binding layer, and
`tests/shared-workflows.spec.js` asserts that.

Registry I/O goes through `createRegistryRepo(path, codec, errorPolicy)` in
`src/storage/provider-registry-repo.ts`; both registries keep their own file, record shape, and
error policy. `src/commands/target-bindings.ts` binds an adapter to the workflows
(`bindTarget` / `bindCodexTarget` / `bindClaudeTarget`), and `src/commands/target-presenters.ts`
maps a target id to its presenter (`presenterFor`) — a pure function from payload to lines, with no
file read, path resolution, or runtime probe. A missing presenter is an internal error, never a
fallback to another target's text.

`src/commands/registry.ts` holds command declarations only; the handler is loaded by
`src/commands/dispatch.ts`, so `--help` and `--version` load no app service, no inquirer runtime, no
Codex probe, and no registry I/O. `tests/load-boundary.spec.js` checks that in a child process, with
a counter-case asserting that a real command does load them.

`src/infra/` and the other legacy `src/cli/` helpers are unused compatibility facades, outside the
live layers. `dist/` is generated by `npm run build`.

## State Boundary

Tool home stores managed state:

```text
agent-provider-switch.json
providers.json
claude-providers.json
.aps.lock
backups/
```

`backups/latest.json` and retention are shared by both targets. The one tool home is resolved by
`APS_HOME`; target runtime roots use `APS_CODEX_DIR` and `APS_CLAUDE_DIR` respectively.

The Codex directory stores active Codex runtime files:

```text
config.toml
auth.json
```

The Claude Code directory stores active `settings.json`.

The app layer should pass explicit paths into storage functions and avoid hidden global filesystem access beyond path resolution.

## Provider Model

`providers.json` stores provider records keyed by local provider name. Each provider points to a managed Codex `model_provider` id through its `profile` field. In current docs and UI, `--profile` is explained as this model-provider id alias.

Managed projection writes:

- top-level `model`
- top-level `model_provider`
- `[model_providers.<id>]` with `name`, `base_url`, `wire_api = "responses"`, and `requires_openai_auth = true`
- `auth.json` API-key projection

New managed writes do not create legacy `[profiles.*]` sections.

`claude-providers.json` stores target-local names with `{ settings, note?, tags? }` records.
`agent-provider-switch.json` may contain `claudeDefaults.settings`. Stored provider settings can
be deltas; effective settings resolve those against defaults and are written to Claude's live
settings.json. Readers used for registry writes preserve raw stored settings. Same-name Codex and
Claude providers are independent.

## Target Scope

The tool serves two targets from one tool home: **Codex**, the default, and **Claude Code**, selected with `--claude`. `src/domain/target.ts` declares `COMMAND_TARGET_POLICIES`, one entry per command id, and it is the only place the answer lives:

| Scope | Commands | Meaning |
|---|---|---|
| `switchable` | `add`, `switch`, `list`, `show`, `current`, `remove` | One shared workflow; the flag picks the adapter, Codex is the default |
| `codex-only` | `init`, `migrate`, `setup`, `edit`, `import`, `export`, `config show`, `config list-profiles` | A Claude target is refused, `--codex` is accepted and inert |
| `claude-only` | `config compact` | The Claude target is required; routes to the Claude handler either way |
| `both` | `status`, `doctor`, `backups list` | Reports on both targets; a flag narrows the report |
| `shared` | `backups prune`, `rollback`, `unlock` | One backups tree, one pointer, one lock; both flags refused |

`--target <id>` is a third spelling of the same selection and is normalized in `parseArgs()` with `--codex` and `--claude`, so nothing downstream re-reads a flag. It is accepted before or after the command tokens, does not take the `=` form, and refuses a missing, flag-shaped, or unknown id. Naming two different targets is `INVALID_ARGUMENT`; repeating one is accepted.

**Scope and capability are different questions**, and the `both` row is where they part. `acceptsTargetFlag(id, "--claude")` is true for `switchable`, `claude-only`, and `both`, while `routesToClaudeHandler(id)` is true only for the first two, because no Claude handler could produce the whole answer for a command whose answer is "here is Codex, here is Claude, here is the lock they share". `policyOf()`, `scopeOf()`, `scopeOfName()`, `acceptsTarget()`, and `resolveCommandTargets()` read the same table.

`resolveCommandTargets(id, options)` answers what an invocation covers: `["codex"]`, `["claude"]`, both ids for a bare `both` command, or `[]` for `shared`. The order is fixed: `executeCommand` runs `assertFlagsApply` (which refuses a flag the command's scope does not accept, the two contradictory flags, and — on `both` — `--codex-dir` alongside a Claude target), then resolves the selection, then assigns `ctx.targets`. A refusal therefore renders `targets: []` with `target: null`: it resolved nothing.

The envelope carries `targets` (authoritative) and `target` (`singleTarget(targets)`, non-null exactly when one id is in scope). Handlers read `ctx.targets`; a target out of scope is not probed at all, and an in-scope but unconfigured target still builds its payload so `configured: false` is reported rather than the section being absent.

The scope table is not a *target descriptor* on its own. What a target contributes is an adapter
under `src/app/targets/`: record schema and registry codec, native plans, matching, defaults
resolution, payload views, and report reads. The shared layer owns orchestration — the mutation
transaction, registry I/O, the chooser, report composition, and presentation dispatch. Target
capabilities describe supported operations, command scope describes accepted and default selection,
and stored formats and native configuration rules stay per-target.
[ADR-0001](./adr/0001-share-provider-workflows-through-target-adapters.md) records that boundary.

## Mutations And Backups

Mutating app services run through `runMutation`, acquire the lock, create backups for affected files, perform writes, and roll back when the mutation fails.

Managed configuration writes include `init`, `migrate`/`setup`, `add`, `edit`, `switch`, `remove`,
`import`, and Claude `config compact`. The six provider verbs reach `runMutation` through
`commitProviderChange()`, which takes one lock and one backup for one logical change; an adapter
declares the affected files and the native changes and never nests another `runMutation()`. Recovery
and pruning use their own shared-lock workflows; export writes an external file atomically.

## Diagnostics

`status` is a lightweight current-state view. `doctor` is issue-first and checks config existence, providers existence, model-provider consistency, auth projection validity, route drift, and Codex CLI availability.

Both cover the two targets and narrow with `--codex` / `--claude`. For Codex the checks above apply; for Claude the registry and the live `settings.json` are checked. An unconfigured target contributes no issue, so a fresh tool home is healthy, and an out-of-scope target is not read — `doctor --claude` runs no Codex probe. Each issue carries its `target`; a leftover lock is the one finding reported once with `target: null`, because it blocks writes for both.

Optional bridge or account-runtime checks are not part of current diagnostics.

## Error Vocabulary

**An error code names a condition and never a target.** The two lines share one vocabulary: `PROVIDER_NOT_FOUND`, `PROVIDERS_NOT_FOUND`, `PROVIDERS_PARSE_ERROR`, and `PROVIDER_ALREADY_EXISTS` are raised by Codex and Claude code alike. A `CLAUDE_`-prefixed code is not permitted anywhere in `src/`; the invariant is asserted by `tests/error-vocabulary.spec.js`.

What distinguishes the two lines is the envelope's `targets` field — the authoritative list of targets the invocation covered — plus `singleTarget(targets)` under `target`, plus the `message`, which keeps naming the target where the state calls for it (`Claude provider "x" was not found.`). Both are written on the failure path too. `target` is `null` for a bare `doctor`/`status`/`backups list` (two targets genuinely in scope) and `null` with `targets: []` for a refusal raised by the flags (nothing resolved); the two cases are told apart by `targets`, not by `target`.

Two codes are one character apart and must stay distinct: `PROVIDER_ALREADY_EXISTS` means a record with that name exists, and `PROVIDERS_ALREADY_EXISTS` means the registry file exists.

The error space and the doctor's *issue* space share some names and are deliberately not unified. An error is a failed run; an issue is a finding on a successful run. `DESTRUCTIVE_REMOVE_BLOCKED` and the other config-issue codes live in the issue space and are not members of `ErrorCode`.

## Removed Runtime Experiments

The current architecture has no runtime paths for Copilot SDK integration, GitHub device-flow
login, HTTP proxy bridges, local bridge workers, bridge logs, or bridge runtime state. Historical
docs describe those experiments.
